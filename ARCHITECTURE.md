# Архитектурные решения

## AD-1. Точка стыковки: forward_protocol.socks5

**Рассмотренные варианты**

| Вариант | Суть | Вердикт |
|---|---|---|
| **A. SOCKS5-upstream** | `[forward_protocol.socks5]` TrustTunnel → socks-inbound Xray | **Принят** |
| B. Reverse proxy TrustTunnel | `[reverse_proxy]` на Xray | Отклонён: транслирует только HTTP/1.1 к origin, не годится для произвольного TCP/UDP |
| C. Прозрачный перехват | iptables REDIRECT/TPROXY + dokodemo-door | Отклонён: хрупко, требует NET_ADMIN, ломается при обновлениях, дублирует то, что уже есть в TrustTunnel штатно |
| D. Форк TrustTunnel | Добавить свой outbound | Отклонён: прямо нарушает правило 1 |

Вариант A — единственный, где обе стороны используют документированный
интерфейс, рассчитанный ровно на такое применение.

## AD-2. Управление конфигом: «база + управляемая секция»

Мост не редактирует чужой файл на месте и не парсит-перезаписывает весь TOML
(это потеряло бы комментарии и неизвестные ему поля будущих версий).
Вместо этого:

```
/etc/ttx/vpn.base.toml        (пишет оператор / setup_wizard)
        │  копируется дословно, вырезается только таблица forward_protocol
        ▼
/opt/trusttunnel/vpn.toml  =  база + маркер + [forward_protocol.socks5]
```

Следствие: любые новые параметры, которые появятся в будущих версиях
TrustTunnel, проходят через мост без изменений в его коде.

## AD-3. Разделение источников правды

| Сущность | Источник правды |
|---|---|
| Пользователи туннеля, сертификаты, listen_address | TrustTunnel (`credentials.toml`, `hosts.toml`, `vpn.base.toml`) |
| Маршрутизация, outbound'ы, geo-правила, лимиты | 3x-ui (панель/БД) |
| Связь между ними (адрес ingress) | ttx-bridge |

Мост намеренно узкий: он владеет ровно одним inbound'ом и ровно одной таблицей
конфига. Всё остальное остаётся под управлением родных инструментов.

## AD-4. Стратегия совместимости версий

1. Версии upstream пинуются (`TT_VERSION`, `XUI_TAG`, `-V` у установщика).
2. `compat.json` фиксирует минимальные и референсные версии и перечень
   используемых API-эндпоинтов и фич.
3. `ttx doctor`/`reconcile` проверяют версию TrustTunnel и фактическую
   работоспособность API 3x-ui; при `compat.strict = true` мост отказывается
   работать с неподдерживаемой версией TrustTunnel.
4. Клиент панели устойчив к появлению новых полей в JSON: читаются только
   нужные ключи, неизвестные игнорируются.

## AD-5. Идемпотентность и безопасность записи

* `write_if_changed` пишет через временный файл и `os.replace` (атомарно),
  предварительно сохраняя `.ttx-bak`.
* Перезапуск TrustTunnel происходит только при фактическом изменении содержимого.
* `guard_loop` отказывается формировать конфиг, создающий петлю трафика.
* Повторный прогон рендера над уже управляемым файлом даёт тот же результат
  (проверено: маркер и секция не дублируются).

## AD-6. Аутентификация панели и граница владения

Для автоматизации предпочтителен Bearer API token 3x-ui: он не зависит от
интерактивной 2FA и не требует cookie/CSRF. Логин с паролем сохранён как
совместимый режим; мост сначала получает `/csrf-token`, затем создаёт сессию.

Ingress считается принадлежащим мосту только при точном совпадении `remark`.
Совпадение порта или протокола не является доказательством владения: иначе мост
мог бы захватить и перезаписать inbound, созданный оператором. Если порт уже
занят чужим inbound, добавление завершится явной ошибкой панели.
