# Архитектурные решения

Нормативная production-топология версии
[0.2.1](REPO_VERSION.md) описана в [SPEC.md §2](SPEC.md#2-архитектура-production-ffkndru).
Ниже сохранены решения reference-схемы TrustTunnel→3x-ui. Они не означают,
что TrustTunnel владеет `443` на текущем production-хосте.

В reference/Compose-схеме публичная точка входа одна: TrustTunnel владеет
`443/tcp+udp`. В production ffknd Nginx владеет только `443/tcp`, Xray Reality
находится на loopback:10443, а TrustTunnel независимо слушает 8443/tcp+udp.

```
Internet :443/tcp+udp
          │
          ▼
TrustTunnel endpoint
    ├── HTTP path /... ──► reverse_proxy ──► 127.0.0.1:8080 ──► ffknd portal
    └── VPN CONNECT ─────► forward_protocol.socks5 ──► Xray/3x-ui :10800
```

## AD-1. Точка стыковки: forward_protocol.socks5

**Рассмотренные варианты**

| Вариант | Суть | Вердикт |
|---|---|---|
| **A. SOCKS5-upstream** | `[forward_protocol.socks5]` TrustTunnel → socks-inbound Xray | **Принят** |
| B. Reverse proxy как транспорт в Xray | `[reverse_proxy]` вместо SOCKS5-upstream | Отклонён: транслирует только HTTP/1.1 к origin, не годится для произвольного TCP/UDP |
| C. Прозрачный перехват | iptables REDIRECT/TPROXY + dokodemo-door | Отклонён: хрупко, требует NET_ADMIN, ломается при обновлениях, дублирует то, что уже есть в TrustTunnel штатно |
| D. Форк TrustTunnel | Добавить свой outbound | Отклонён: прямо нарушает правило 1 |

Вариант A — единственный, где обе стороны используют документированный
интерфейс, рассчитанный ровно на такое применение. Это не запрещает отдельный
`[reverse_proxy]` для обычного сайта: он обслуживает только браузерные
HTTP-запросы и не заменяет туннельный SOCKS5-upstream.

## AD-2. Управление конфигом: «база + управляемая секция»

Мост не редактирует чужой файл на месте и не парсит-перезаписывает весь TOML
(это потеряло бы комментарии и неизвестные ему поля будущих версий).
Вместо этого:

```
/etc/ttx/vpn.base.toml        (пишет оператор / setup_wizard)
        │  копируется дословно, вырезается только таблица forward_protocol
        ▼
/opt/trusttunnel/vpn.toml  =  база + маркер + [forward_protocol.socks5]
```

Следствие: любые новые параметры, которые появятся в будущих версиях
TrustTunnel, проходят через мост без изменений в его коде.

## AD-3. Разделение источников правды

| Сущность | Источник правды |
|---|---|
| Пользователи туннеля, сертификаты, listen_address | TrustTunnel (`credentials.toml`, `hosts.toml`, `vpn.base.toml`) |
| Маршрутизация, outbound'ы, geo-правила, лимиты | 3x-ui (панель/БД) |
| Связь между ними (адрес ingress) | ttx-bridge |

Мост намеренно узкий: он владеет ровно одним inbound'ом и ровно одной таблицей
конфига. Всё остальное остаётся под управлением родных инструментов.

## AD-4. Стратегия совместимости версий

1. Версии upstream пинуются (`TT_VERSION`, `XUI_TAG`, `-V` у установщика).
2. `compat.json` фиксирует минимальные и референсные версии и перечень
   используемых API-эндпоинтов и фич.
3. `ttx doctor`/`reconcile` проверяют версию TrustTunnel и фактическую
   работоспособность API 3x-ui; при `compat.strict = true` мост отказывается
   работать с неподдерживаемой версией TrustTunnel.
4. Клиент панели устойчив к появлению новых полей в JSON: читаются только
   нужные ключи, неизвестные игнорируются.

## AD-5. Идемпотентность и безопасность записи

* Итоговый текст проходит `tomllib`-валидацию до любого изменения
  target-файла; параллельные watch/timer/manual apply сериализуются file lock.
* Состояние существующего target перед apply фиксируется в памяти и в
  `.ttx-bak`; запись и восстановление существующего файла идут через `fsync` +
  `os.replace` с сохранением режима и владельца. Если target до apply не было,
  rollback удаляет созданный файл и фиксирует изменение каталога через `fsync`.
* Перезапуск происходит только при фактическом изменении. За restart следует
  ограниченный по времени `systemctl is-active`; ошибка любого шага возвращает
  состояние до apply, повторно запускает прежнюю конфигурацию и возвращает ошибку.
* `guard_loop` отказывается формировать конфиг, создающий петлю трафика.
* Повторный прогон рендера над уже управляемым файлом даёт тот же результат
  (проверено: маркер и секция не дублируются).

## AD-6. Аутентификация панели и граница владения

Для автоматизации предпочтителен Bearer API token 3x-ui: он не зависит от
интерактивной 2FA и не требует cookie/CSRF. Логин с паролем сохранён как
совместимый режим; мост сначала получает `/csrf-token`, затем создаёт сессию.

Ingress считается принадлежащим мосту только при точном совпадении `remark`.
Совпадение порта или протокола не является доказательством владения: иначе мост
мог бы захватить и перезаписать inbound, созданный оператором. Если порт уже
занят чужим inbound, добавление завершится явной ошибкой панели.

## AD-7. Один публичный 443 для туннеля и портала

TrustTunnel остаётся единственным процессом, который привязывает публичные
`443/tcp` и `443/udp`. В базовом `vpn.toml` используется отдельный origin:

```toml
[reverse_proxy]
server_address = "127.0.0.1:8080"
path_mask = "/"
h3_backward_compatibility = false
```

Обычные HTTP/1.1, HTTP/2 и HTTP/3-запросы с путём `/...` передаются origin как
HTTP/1.1. Запрос VPN-клиента использует authority-form `CONNECT`, не совпадает
с `path_mask = "/"` и продолжает обрабатываться как туннель через
`[forward_protocol.socks5]`. Портал поэтому не слушает публичный интерфейс и не
участвует в VPN data path.

Отказ портала делает недоступной веб-страницу, но не должен останавливать
`CONNECT`: между `trusttunnel.service` и `ffknd-portal.service` нет зависимости
`Wants=` или `Requires=`. TrustTunnel запускается, даже если портал не настроен или выключен.
Фактическую независимость после изменения конфигурации подтверждает внешний
`tests/port443-smoke.sh`, который проверяет и HTTPS GET, и VPN CONNECT.

## AD-8. Портал: стандартная библиотека Python и локальная криптография

Backend портала написан на стандартной библиотеке Python 3.11+:
`ThreadingHTTPServer` обслуживает API и статику, `sqlite3` хранит серверное
состояние, миграции применяются при старте, база работает в WAL-режиме. Внешних
Python-зависимостей нет. SQLite содержит хеши сессий, проверки сервисов,
RSS/Atom-источники и элементы ленты, короткие ссылки и счётчики переходов.

Один пароль входа хранится только как `PORTAL_PASSWORD_HASH` (PBKDF2-SHA256).
После входа сервер выдаёт случайную HttpOnly/Secure/SameSite=Strict cookie;
в базе остаётся хеш токена, а изменяющие запросы требуют CSRF-токен и совпадение
Origin. Управление сервисами, лентами и короткими ссылками закрыто сессией.

Блокнот имеет отдельную границу безопасности. Web Crypto выводит ключ из
мастер-пароля через PBKDF2-SHA256 и шифрует JSON с заметками AES-256-GCM.
Шифротекст хранится в `localStorage`; мастер-пароль, ключ и открытый текст не
отправляются API и не попадают в SQLite. Веб-инструменты и генератор QR также
работают локально в браузере. Технический справочник читается из Markdown-файлов
в `portal/content/reference/`.

RSS и мониторинг делают исходящие HTTP(S)-запросы с защитой от SSRF: по
умолчанию разрешены только глобальные адреса и порты 80/443, DNS-ответ
проверяется до соединения, а соединение закрепляется за проверенным IP.

## AD-9. Изоляция портала в bare-metal и Compose

В bare-metal режиме `ffknd-portal.service` запускается непривилегированным
пользователем `ttx-portal`, слушает `127.0.0.1:8080`, пишет только в
`/var/lib/ffknd-portal` и ограничен systemd sandboxing. Секретный env-файл
`/etc/ttx/portal.env` имеет режим `0600`.

В Compose контейнер запускается как `portal`, не имеет секции `ports` и
использует `network_mode: "service:trusttunnel"`. Это даёт двум контейнерам
общий loopback: portal слушает `127.0.0.1:8080`, а TrustTunnel обращается туда
без публикации origin в Docker-сеть или на хост. Единственные публичные
пробросы остаются у TrustTunnel: `443:8443/tcp` и `443:8443/udp`.
Обычный restart контейнера TrustTunnel сохраняет этот namespace; при его
пересоздании portal тоже нужно пересоздать, чтобы присоединить к новому namespace.
